# AdaptiveTraffic

Школьный научно-инженерный проект: «Разработка и исследование адаптивного
алгоритма управления светофорным объектом в условиях неравномерного
транспортного потока». Секция — «Инновации умного города».

Исследовательский вопрос: можно ли уменьшить задержку автомобилей при
неравномерном и изменяющемся потоке, управляя зелёными фазами по очередям
и времени ожидания, в сравнении с фиксированным циклом?

Гипотеза: такое управление уменьшит среднюю задержку без чрезмерного
увеличения ожидания отдельных направлений. Это **проверяемая гипотеза**,
а не обещание, что ADAPTIVE всегда лучше.

## Что уже работает

Один перекрёсток, четыре направления, движение только прямо. NORTH/SOUTH
обслуживаются совместной фазой NS, EAST/WEST — фазой EW. Очередь каждого
направления обслуживается независимо. Шаг — 1 с, интервал между проездами
на одном направлении — 2 с. Расчёт выполняется как модель очередей у стоп-линии;
отдельный pygame GUI показывает её состояние и уже разрешённые проезды.

- FIXED чередует зелёные по 30 с, жёлтый по 3 с, общий красный по 1 с.
- ADAPTIVE принимает решение по пяти заданным проверкам: минимальный зелёный,
  пустая текущая сторона, максимальное ожидание, максимальный зелёный, приоритет.
- QUEUE_ONLY использует те же ограничения, включая MAX_WAIT, но его обычный
  приоритет равен только очереди. У ADAPTIVE: `queue + oldest_wait / WAIT_EQUIVALENT`.
- Пешеходная кнопка создаёт один запрос на отдельную безопасную фазу, во время
  которой все автомобильные сигналы красные.
- Контроллер просит переключение; отдельный автомат гарантирует путь через
  жёлтый и общий красный. На этих интервалах движение запрещено.
- Неизменяемый `TrafficPlan` генерируется заранее. FIXED и ADAPTIVE в паре
  получают **один и тот же объект плана**, но собственные очереди и машины.
- После генерации оставшиеся автомобили обслуживаются до полного освобождения
  перекрёстка. Тайм-аут явно помечает незавершённый опыт.
- Результаты, параметры и решения сохраняются; анализ строит четыре графика.

Основной симулятор использует только стандартную библиотеку Python.
`pytest` нужен для тестов, `matplotlib` — для графиков, `pygame` — только для GUI.
ESP32, реальные датчики, компьютерное зрение и машинное обучение не реализованы.

## Установка и тесты

Нужен Python 3.10 или новее. Команды выполняются из корня проекта.

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
pytest -q
```

В Windows PowerShell активация: `.venv\Scripts\Activate.ps1`.
Без активации в Linux можно использовать `.venv/bin/python` и `.venv/bin/pytest`.

Pygame включён в `requirements.txt`. Отдельная установка:
`python -m pip install "pygame>=2.6,<3"`. Если для вашей версии Python нет готового
wheel, pip собирает pygame из исходников: нужны компилятор и SDL2/SDL2_ttf.
При отсутствии SDL2_ttf в Arch Linux: `sudo pacman -S --needed sdl2_ttf`, затем
`python -m pip install --no-cache-dir --force-reinstall "pygame>=2.6,<3"`.
В текущем окружении Python 3.14 pygame уже собран с локальной SDL2_ttf внутри
`.venv`; системные пакеты не менялись. Виртуальное окружение в Git не включается.
Локальная сборка может предупреждать об отсутствии оптимизации AVX2: это касается
скорости рисования, а не логики симуляции. Снимки smoke-теста сохранены через BMP,
поскольку в этой сборке нет поддержки расширенных форматов pygame.image.

## Запуск

Один опыт с фиксированным контроллером FIXED:

```bash
python main.py --controller fixed --scenario ns_heavy --seed 42
```

Один опыт с адаптивным контроллером ADAPTIVE:

```bash
python main.py --controller adaptive --scenario ns_heavy --seed 42
```

Один опыт с QUEUE_ONLY:

```bash
python main.py --controller queue_only --scenario ns_heavy --seed 42
```

Парное сравнение на десяти seeds, начиная с 42:

```bash
python -m adaptive_traffic.experiments --scenario ns_heavy --runs 10 --seed 42 --output results/ns_comparison
```

Все семь сценариев, по пять seeds и два контроллера (70 запусков):

```bash
python main.py --scenario all --runs 5 --seed 42 --output results/my_check
python -m adaptive_traffic.analyze results/my_check/results.csv
```

Сравнение трёх контроллеров:

```bash
python main.py --controller all --scenario ns_heavy --runs 10 --seed 42 --output results/three_controllers
python -m adaptive_traffic.analyze results/three_controllers/results.csv
```

`--controller both` и запуск без `--controller` по-прежнему сравнивают FIXED
и ADAPTIVE; `--controller all` добавляет QUEUE_ONLY. `--scenario all` выбирает
сценарии, не контроллеры. Headless-команды не импортируют pygame и не открывают
окно. По умолчанию пешеходных запросов в экспериментах нет.

`--duration 1800` задаёт время генерации в секундах, `--drain-timeout 1800` —
дополнительный предел обслуживания после неё. `--controller both` используется
по умолчанию. Названия сценариев и контроллеров можно писать в любом регистре.
`--runs 5 --seed 42` означает seeds 42, 43, 44, 45, 46.

Если `--output` не указан, создаётся новая папка `results/run_<дата_время>`.
Указанная папка эксперимента должна быть новой: исходные данные не перезаписываются.
Полный список аргументов: `python main.py --help`.

Если хотя бы один запуск не завершился, CSV всё равно сохраняется, в нём будет
`completed_successfully=False`, в консоли — `INCOMPLETE`, код возврата команды — 1.
Разбирать такой результат как успешный нельзя.

## GUI и пешеходная кнопка

```bash
python main.py --visualize --controller adaptive --scenario ns_heavy --seed 42
python main.py --visualize --controller fixed --scenario ns_heavy --seed 42
python main.py --visualize --controller queue_only --scenario ns_heavy --seed 42
```

GUI требует один контроллер, один сценарий и один seed. Окно — 1200×800.
Панель показывает состояние автомата, очереди, ожидания, приоритеты, последнее
решение и причину переключения, статистику машин и статус пешехода.
У FIXED приоритет отображается как N/A.

| Клавиша | Действие |
|---|---|
| SPACE | Пауза / продолжение |
| R | Начать тот же опыт заново |
| 1 / 2 / 3 | Темп x1 / x5 / x20 |
| P | Создать пешеходный запрос |
| F / Q / A | Перезапустить с FIXED / QUEUE_ONLY / ADAPTIVE |
| ESC | Закрыть окно |

При перезапуске используется тот же TrafficPlan; очереди, ручные запросы и
статистика сбрасываются. Ускорение меняет частоту вызова Simulation.step(),
а не длительность модельного шага. Пауза останавливает модель и анимацию.
На паузе P создаёт запрос, но время его ожидания не растёт. После завершения
опыта P игнорируется; R начинает опыт заново.

Видны до восьми машин на каждом направлении, остальные отмечены как `+N offscreen`.
Точная очередь всегда есть в панели. Только уже обслуженные Simulation машины
получают анимацию проезда длительностью одну модельную секунду; это не новая
физика движения. При x20 анимация короткая. `Cars generated` показывает уже
добавленные машины / весь план. Приоритеты показывают текущие очереди после шага,
а решение относится к последнему шагу и могло использовать очередь до обслуживания.
В журнале сохранены именно значения на момент принятия решения.

Повторные P объединяются, пока текущий запрос не прошёл весь цикл:

```text
NS_GREEN → NS_YELLOW → ALL_RED_TO_PED → PED_GREEN
         → PED_CLEARANCE → ALL_RED_AFTER_PED → EW_GREEN
```

При обычном переключении после PED возвращаемся к его целевой фазе. Если только
PED_MAX_WAIT вызвал обслуживание, FIXED продолжает чередование, ADAPTIVE выбирает
больший свой приоритет, QUEUE_ONLY — большую очередь. При равенстве выбирается
противоположная текущей фаза. MIN_GREEN при пешеходном вмешательстве соблюдается.
Пешеходный сигнал зелёный только на PED_GREEN; на всех остальных состояниях красный.
Запрос сбрасывается после всего цикла; ожидание замораживается при начале PED_GREEN.

Для воспроизводимого опыта с пешеходами задайте одинаковое расписание запросов:

```bash
python main.py --controller all --scenario ns_heavy --seed 42 --pedestrian-times 5 60 120 --output results/pedestrians
python main.py --visualize --controller adaptive --scenario ns_heavy --seed 42 --pedestrian-times 5 60 120
```

Времена задаются по возрастанию в секундах, строго до окончания генерации.
Расписание сохраняется в metadata.json и передаётся всем контроллерам одинаково.
Повторные запросы до конца обслуживания объединяются, как P. Равенство GUI/headless
проверяется при одинаковом плане и расписании; дополнительные ручные P меняют
входные события. GUI не сохраняет CSV: для анализа используйте headless с расписанием.

## Файлы результатов и анализ

В папке каждого эксперимента:

```text
results.csv               — одна строка на сценарий, seed и контроллер
diagnostics.csv           — причины переключений, длительности, доля переходов
metadata.json             — все параметры, интенсивности, seeds, версия Python
switches/                 — отдельный журнал решений для каждого запуска
analysis/summary.csv      — среднее и выборочное стандартное отклонение по seeds
analysis/comparison.csv   — парные разности и относительное улучшение
analysis/pairwise_comparison.csv — все пары, включая QUEUE_ONLY → ADAPTIVE
analysis/analysis_report.txt — число полных пар и причины исключения остальных
analysis/*.png, *.svg     — четыре графика, в двух форматах
```

Графики: `mean_wait`, `p95_wait`, `mean_queue`, `total_clearing_time`.
Полосы на столбцах — выборочное стандартное отклонение результатов по seeds,
**не** доверительные интервалы. PNG подходит для вставки в презентацию,
SVG можно масштабировать без потери чёткости. Окна не открываются.

```bash
python -m adaptive_traffic.analyze results/ns_comparison/results.csv
python -m adaptive_traffic.analyze results/ns_comparison/results.csv --no-plots
```

Анализ выбирает пару FIXED/ADAPTIVE либо тройку, если CSV содержит QUEUE_ONLY.
Графики и summary.csv показывают соответственно два или три алгоритма.
Если один запуск отсутствует или не завершён, исключается весь seed для всех
сравниваемых контроллеров; причина записывается в отчёт. Если полных групп нет,
анализ возвращает код 1. Исключение неполных групп само может вносить
смещение: сначала разберите причины тайм-аутов, затем делайте выводы.

Для задержек, очередей и полного времени:

```text
improvement_percent = (mean_FIXED - mean_ADAPTIVE) / mean_FIXED * 100
```

Положительное значение означает улучшение. Для количества обслуженных машин
направление разности обратное; при полном завершении пары это количество равно.
Это количество, а не скорость обслуживания (throughput). При нулевой базе процент
не определён: поле остаётся пустым. У числа переключений, количества созданных
машин и заданной длительности генерации нет самостоятельного смысла «лучше/хуже»;
процент улучшения для них не приписывается.

Средние считаются с одинаковым весом каждого seed. Процент — отношение средних,
а не среднее процентов. `fixed_minus_adaptive_mean/std` относятся к парным
разностям FIXED − ADAPTIVE; при одном seed выборочное отклонение не определено.
Не объединяйте запуски с разными параметрами в один CSV для этого анализа.

`comparison.csv` сохраняет прежние поля FIXED/ADAPTIVE. В `pairwise_comparison.csv`
положительный процент означает улучшение `controller` относительно `baseline`.
Для трёх алгоритмов там есть FIXED → QUEUE_ONLY, FIXED → ADAPTIVE и QUEUE_ONLY → ADAPTIVE.

## Диагностика переключений

Каждая headless-серия сохраняет `diagnostics.csv` рядом с `results.csv`.
Строки соединяются по `scenario`, `controller`, `seed`; флаг завершения также сохранён.

| Поля | Определение |
|---|---|
| switches_EMPTY_CURRENT, switches_MAX_WAIT, switches_MAX_GREEN, switches_HIGHER_PRIORITY | Число запросов смены по каждой причине |
| switches_FIXED_TIMER, switches_PED_MAX_WAIT | Запросы таймера FIXED и пешеходного тайм-аута для полного учёта |
| average_green_duration | Средняя наблюдённая длительность автомобильных зелёных участков |
| total_yellow_time | Время в NS_YELLOW и EW_YELLOW, с |
| total_all_red_time | Время во всех ALL_RED-состояниях, включая до/после PED, с |
| transition_time_fraction | `(total_yellow_time + total_all_red_time) / total_clearing_time`, доля от 0 до 1 |

Учитывается весь опыт, включая drain. Последний зелёный включается в наблюдённой,
возможно усечённой длительности: поэтому средний FIXED может быть чуть меньше 30 с.
PED_GREEN и PED_CLEARANCE не входят в числитель доли переходов: она измеряет только
YELLOW и ALL_RED. При обычной смене с вставленным PED сохраняется автомобильная
причина; PED_MAX_WAIT записывается только когда именно пешеход потребовал смены.

## Стартовые параметры

Все значения находятся в [adaptive_traffic/config.py](adaptive_traffic/config.py).

| Параметр | Значение | Смысл |
|---|---:|---|
| TIME_STEP | 1 с | Шаг модели |
| VEHICLE_HEADWAY | 2 с | Интервал проезда на каждом направлении |
| FIXED_GREEN | 30 с | Зелёный FIXED |
| YELLOW / ALL_RED | 3 / 1 с | Защитные интервалы |
| MIN_GREEN / MAX_GREEN | 10 / 45 с | Минимум и условный максимум ADAPTIVE |
| MAX_WAIT | 60 с | Порог запроса переключения по ожиданию |
| WAIT_EQUIVALENT | 10 с | Сколько секунд ожидания добавляют единицу приоритета |
| SWITCH_MARGIN | 1,5 | Минимальный перевес приоритета; сравнение строгое |
| SIMULATION_DURATION | 1800 с | Активная генерация |
| DRAIN_TIMEOUT | 1800 с | Дополнительное время до аварийного завершения |
| PED_MAX_WAIT | 40 с | Порог запроса безопасного пешеходного обслуживания |
| PED_GREEN / PED_CLEARANCE | 10 / 3 с | Пешеходный зелёный и освобождение перехода |

В Python эти имена записаны строчными буквами: например `config.min_green`.
Длительности фаз, генерации, headway и тайм-аута должны быть кратны шагу.
`MAX_GREEN` разрешается превысить, если другая сторона пуста.
`MAX_WAIT` **не гарантирует**, что каждый автомобиль проедет за 60 секунд:
после запроса остаются защитные интервалы, обслуживание и очередь впереди.

Исследование `WAIT_EQUIVALENT` выполняется отдельными сериями с одинаковыми seeds:

```bash
for value in 5 10 15 20; do
  python main.py --scenario all --runs 10 --seed 42 --wait-equivalent "$value" --output "results/wait_$value"
  python -m adaptive_traffic.analyze "results/wait_$value/results.csv"
done
```

Эта серия автоматически не запускалась. Значение 10 с — исходная настройка,
не научно обоснованный оптимум. Увеличивайте число seeds до 50–100 для дальнейшего
исследования, сохраняя проигрыши и все исходные данные.

## Сценарии

Интенсивности — **на отдельное направление**, в авто/мин. N/S и E/W в таблице
означают одинаковую интенсивность на каждом из двух направлений, не сумму фазы.

| Сценарий | NORTH / SOUTH | EAST / WEST | Изменение во времени |
|---|---:|---:|---|
| BALANCED_LOW | 4 / 4 | 4 / 4 | Постоянно |
| BALANCED_HIGH | 12 / 12 | 12 / 12 | Постоянно |
| NS_HEAVY | 20 / 20 | 4 / 4 | Постоянно |
| EW_HEAVY | 4 / 4 | 20 / 20 | Постоянно |
| RUSH_HOUR | 6 → 18 | 6 → 18 | Рост после половины времени |
| CHANGING_FLOW | 18 → 8 → 4 | 4 → 8 → 18 | Три равные части |
| MINOR_ROAD | 18 / 18 | 0,5 / 0,5 | Постоянные интенсивности, редкие случайные приезды EW |

Интенсивности заданы до технического прогона и по его результатам не менялись.
Непрерывно зелёное направление может обслужить примерно 30 авто/мин. FIXED
выделяет ему 30/68 всего времени: около 13,24 авто/мин. Поэтому BALANCED_HIGH
близок к пределу FIXED, тяжёлая сторона в NS_HEAVY/EW_HEAVY перегружает FIXED,
а вторая половина RUSH_HOUR перегружает обе фазы. Это намеренно разные условия,
а не обещание преимущества ADAPTIVE. Для исследования нужны и дополнительные
промежуточные нагрузки. Начальная фаза NS одинакова у обоих контроллеров и может
влиять на короткие опыты; зеркальные сценарии не обязаны дать одинаковые числа.

## Выполненная техническая проверка

При разработке локально создан `results/demo/results.csv`:
семь сценариев, seeds 42–46, генерация 1800 с, стартовые параметры. Все 70 запусков
завершены. Анализ и графики сохранены локально в `results/demo/analysis/`.
Результаты не зашиты в программу; эта папка исключена из Git через `.gitignore`.
В GitHub этих файлов нет. После клонирования результаты можно воспроизвести:

```bash
python main.py --scenario all --runs 5 --seed 42 --output results/demo
python -m adaptive_traffic.analyze results/demo/results.csv
```

Папка `results/demo` перед запуском должна отсутствовать; для повторного опыта
укажите новое имя папки.

Например, в этих данных среднее по seeds ожидание в BALANCED_HIGH составляет
33,38 с у FIXED и 132,47 с у ADAPTIVE; в NS_HEAVY — 397,89 и 39,98 с.
ADAPTIVE также проиграл в RUSH_HOUR. Пять seeds — техническая проверка;
по ней нельзя утверждать общую эффективность или подтверждение гипотезы.

Перед добавлением GUI сохранены 42 исходных запуска (seeds 42–44, семь сценариев,
FIXED/ADAPTIVE) в `results/baseline_before_gui/`. Базовый код — коммит `1a97cf1`.
Новая серия `results/gui_stage_smoke/` содержит 63 запуска: те же сценарии/seeds,
теперь FIXED/QUEUE_ONLY/ADAPTIVE. Все завершились. 42 прежние строки результатов
и журналы решений совпали с базой; текст класса AdaptiveController не изменился.

В BALANCED_HIGH средний зелёный ADAPTIVE составил примерно 10,28 с, доля переходов
27,9%; у FIXED — 29,58 с и 11,7%. Это наблюдения на трёх seeds, не доказательство
общей эффективности; настройки по ним не подбирались. Дополнительная серия
`results/pedestrian_smoke/` проверяет три контроллера с запросами в 0, 5 и 60 с
при генерации 120 с; неполных запусков нет.

## Архитектура и маршрут изучения

Файлы сгруппированы по задачам, без отдельного класса для каждой операции:

| Файл | Что изучить |
|---|---|
| [config.py](adaptive_traffic/config.py) | Все параметры и профили спроса |
| [models.py](adaptive_traffic/models.py) | Автомобиль, направления, снимок очередей |
| [traffic_demand.py](adaptive_traffic/traffic_demand.py) | Неизменяемый план, экспоненциальные интервалы |
| [scenarios.py](adaptive_traffic/scenarios.py) | Превращение сценария в участки интенсивности |
| [controllers.py](adaptive_traffic/controllers.py) | Формула приоритета и пять проверок ADAPTIVE |
| [traffic_light.py](adaptive_traffic/traffic_light.py) | Шесть безопасных состояний |
| [simulation.py](adaptive_traffic/simulation.py) | Очереди, порядок шага, проезд, drain и тайм-аут |
| [metrics.py](adaptive_traffic/metrics.py) | Ожидание, очередь и определение p95 |
| [experiments.py](adaptive_traffic/experiments.py) | Одна входная последовательность для пары, CSV |
| [analyze.py](adaptive_traffic/analyze.py) | Парный анализ, знаки процентов, графики |
| [presentation.py](adaptive_traffic/presentation.py) | Данные панели, пауза, перезапуск и часы без pygame |
| [gui.py](adaptive_traffic/gui.py) | Рисование и клавиши; правил движения здесь нет |

`main.py` — короткая точка входа. `tests/` содержит восемь файлов проверок.
Чтобы позже добавить контроллер, достаточно реализовать `name` и метод `decide`
с тем же интерфейсом и подключить его к запуску. Симулятор переписывать не нужно.
Пешеходная обвязка находится в Simulation и TrafficLight, не в AdaptiveController.
По умолчанию расписание запросов пустое и сохраняется исходное автомобильное поведение.

Перед защитой обязательно разберите `calculate_priority`, `AdaptiveController.decide`,
`NEXT_STATE`, `TrafficLight.advance`, `Simulation.step`, `generate_traffic_plan`,
`run_comparison` и `percentile`. Затем вручную проследите одну машину и одно
переключение, сверив их с тестами. Основные пояснения:
[алгоритм](docs/algorithm.md), [модель и ограничения](docs/simulation_model.md).

Этап с GUI, QUEUE_ONLY, пешеходами и диагностикой завершён.
AdaptiveV2, подбор параметров и аппаратная часть не добавлялись.
